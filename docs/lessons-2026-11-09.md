# Lessons from the MindScope live incident (2026-11-09)

Analysis of a real production incident and the changes proposed from it. This file exists so
another agent can review the claims before they are merged. Each claim lists its evidence.

## 1. Shipyard template bug: onboarding page can trap a new user

Claim: in `template/src/app/profile/edit/profile-form.tsx`, calling `router.replace("/")`
and `router.refresh()` back to back races, and the refresh cancels the replace navigation.
The PATCH to `/api/profile` succeeds (profile saved, `onboarding_complete = true`) but the
page never leaves `/profile/edit`.

Evidence:
- Reproduced against the live MindScope app: PATCH returned 200, the page re-rendered as
  "Edit your profile" (onboarding finished) but the URL stayed `/profile/edit` for 16+
  seconds with no navigation. On the local dev server the same code sometimes navigates and
  sometimes does not (classic race; live latency widens the window).
- The same two lines exist unchanged in this repo's template (checked before this PR).

Fix (this PR): one line, `window.location.replace("/")` — a full navigation. Onboarding is a
once-per-lifetime page, so the reload cost is fine, and it guarantees the proxy re-runs with
the fresh session state.

## 2. Shared Supabase projects: one app's trigger can erase every password

Claim: a trigger named `clear_password_on_first_confirm` on `auth.users` (installed by
another app on the shared 6x7 project) sets `encrypted_password := ''` whenever
`email_confirmed_at` transitions from NULL to set. Creating users with
`admin.createUser({ email_confirm: true, password })` therefore produces accounts that can
never sign in; every account on the project (owner included) ended up with
`length(encrypted_password) = 0`.

Evidence:
- `select tgname, pg_get_triggerdef(oid) from pg_trigger where tgrelid = 'auth.users'::regclass and not tgisinternal;`
  lists the trigger and its definition (BEFORE UPDATE OF email_confirmed_at, sets
  `new.encrypted_password := ''`).
- `select email, length(encrypted_password) from auth.users` showed 0 for every account.
- Direct experiment: `createUser(email_confirm: true, password)` then password login
  returned `invalid_credentials`; setting the password again via `updateUserById` made login
  succeed. Split creation (no password + confirm, then password in a second call) is immune.

Changes proposed from this:
- The sign-up pattern fix is in the app (MindScope), not Shipyard, but the diagnostic
  runbook (`skills/ops/references/auth-shared-project.md`, this PR) is the transferable part.

## 3. Redirect-based auth is unsafe on shared projects

Claim: a Supabase project has ONE Site URL. The shared project's Site URL points at a
different app, so emailed magic links land there, not on the app that generated them.

Evidence: `admin.generateLink` produced an `action_link` that redirected to
`commitr.6x7.gr` (the other app) after the token was consumed.

Transfer: `auth-shared-project.md` documents password-first flows and explicit
`redirect_to` for anything emailed.

## 4. A throwaway-user live smoke test catches what verify cannot

Claim: Shipyard `verify` skips sign-in and privacy checks on shared projects, so regressions
in the signed-in experience (broken sign-in, a settings page that crashes, onboarding
traps) went live undetected. A smoke script that creates a throwaway user, signs in through
the real form, completes onboarding, walks the pages, flips theme packs/modes and captures
console/network errors catches all of the above.

Evidence: the MindScope run of the script caught the onboarding trap (claim 1) and earlier
caught the settings infinite-render loop before they were fixed; it passes end to end on
live after each fix.

Transfer: `template/scripts/live-smoke.mjs` (this PR) plus an npm `smoke` script, so new
apps get it out of the box. App-specific knobs are one CONFIG block. Notable implementation
details worth reviewing: onboarding requires waiting for hydration before filling (or the
form submits natively), `net::ERR_ABORTED` on navigation is ignored as noise, and the test
user is deleted at the end (admin API).

## 5. shadcn + theme packs integration recipe

Claim: a naive shadcn init breaks Shipyard theme packs by redefining `--muted`, `--accent`,
`--card`, `--border` with fixed values, adding a dead `.dark` block (Shipyard uses
`data-theme`, not a class), and overriding the app font.

Evidence: v0 (Vercel's builder) produced exactly this integration on the MindScope repo
(branch `v0/chatgpt-ui`, no PR). Reviewing its diff showed the static oklch token block, the
`.dark` block, and the Geist font override; the fix re-mapped shadcn's tokens onto Shipyard's
variables via `@theme inline` and re-keyed the dark variant to `[data-theme="dark"]`.

Transfer: `skills/design/references/shadcn-theme-packs.md` (this PR).

## Open questions for the reviewer

1. Is `window.location.replace("/")` acceptable in the template, or should the template keep
   router navigation and only drop the `refresh()` call? (The full navigation was chosen
   because it is deterministic; dropping refresh alone was not stress-tested.)
2. Should `live-smoke.mjs` live in `template/scripts/` (every new app) or only as a
   reference for apps that want it?
3. `auth-shared-project.md`: the trigger itself was left in place (it belongs to another
   app). Is documenting the runbook enough, or should Shipyard warn when it detects
   foreign triggers on `auth.users` during `verify`?
